# Parser edge case files

Files that exercise specific parser quirks, boundary conditions, or
backwards-compatibility behaviors. Each file is documented with its source,
what it tests, and the expected parser behavior.

## Files

### `23andme_lookalike_rejected_by_PA.txt`
- **Source:** Synthetic, written by hand. Every row is invented.
- **What it is:** A 3-genotype file shaped like 23andMe (4 tab columns)
  but with a single user-written comment `# results of my home panel test
  (placeholder text)` as the only header. Not from 23andMe.
- **What it tests:** The v1.1.0 23andMe canonical-header check. Before v1.1.0
  the 23andMe parser auto-detected on any "23andMe" substring anywhere in
  comments — this file's user-written comment wouldn't have triggered
  detection (no "23andMe" mention), but other lookalikes would have. The check
  requires the canonical `# This data file generated by 23andMe` prefix
  before accepting the file.
- **Expected behavior:** `allelix stats` returns `Error: Allelix doesn't recognise the format of …`.

### `23andme_format_from_genes_for_good_service.txt`
- **Source:** openSNP user4735, file 4081. The "Genes for Good" research
  service (University of Michigan) exports user data in 23andMe format.
  Provenance: CC0.
- **What it is:** A genuine 23andMe-format file (canonical first-line
  `# This data file generated by 23andMe at: ...`) exported by a different
  service. Although it came from Genes for Good, the file starts with
  23andMe's banner, so it is read as 23andMe. The Genes for Good reader is
  for the download whose first line starts `# Genes for Good v`.
- **What it tests:** Parser format auto-detection is content-driven (not
  filename-driven). A file exported by a non-23andMe service in 23andMe
  format must still parse cleanly as 23andMe.
- **Expected behavior:** `allelix stats` reports format `23andMe`, build
  `GRCh37`, ~960K variants.

### `ftdna_grch36_positions.csv`
- **Source:** openSNP user1084, file 597 (FTDNA). Provenance: CC0.
- **What it is:** An FTDNA file with chromosomal positions on the GRCh36
  reference, not GRCh37. FTDNA files don't carry a build declaration in any
  header, so the parser has no in-band signal to distinguish builds.
- **What it tests:** The build decision recognizes GRCh36 from positions
  in a file that states no build (ADR-0044). It also pins the
  unsupported-modern-cache warning path.
- **Expected behavior:** All four known-SNP positions in the file match
  GRCh36, so `allelix analyze` prints `Build: GRCh36 (from known-SNP
  positions: 4/4 match GRCh36)` and warns that ClinVar and the GRCh38-only
  enrichment sources (gnomAD, AlphaMissense, CADD) are unavailable.
  ClinPGx annotations still fire. GWAS Catalog risk alleles and
  single-base SNPedia genotypes are not assessed (counted in
  `strand_abstentions`).
  `allelix stats` shows the same build. (Before two GRCh36 seed positions
  were corrected against dbSNP, this file voted a tentative 3/4, which
  ADR-0025's fail-safe also kept on GRCh36.)

### `unsupported_decodeme.txt`
- **Source:** openSNP user3400, file 2218. Provenance: CC0.
- **What it is:** a gzipped four-column table (`SNP,Chr,Allele1,Allele2`,
  no positions) labelled deCODEme on openSNP. It is not the
  `deCODEme_scan.csv` layout that Allelix reads.
- **What it tests:** a file no reader recognises is rejected cleanly.
- **Expected behavior:** `allelix stats` returns `Error: Allelix doesn't recognise the format of …`.

### `unsupported_23andme_exome_vcf.txt`
- **Source:** Synthetic, written by a script. Every record is invented:
  invented positions and alleles, rsIDs in the rs3999991000 range or `.`,
  a placeholder `##GATKCommandLine` and one sample column named `SAMPLE1`.
- **What it is:** About 5,000 exome-style variant calls in the shape a
  GATK HaplotypeCaller pipeline writes (VCFv4.1, b37 contig lengths, SNVs,
  indels, a few multi-allelic sites, haploid calls on Y and MT). The
  `unsupported_` prefix records its v1.x history; VCF support shipped later
  and the fixture name remains stable.
- **What it tests:** Content-based VCF recognition even when the filename
  misleadingly suggests a 23andMe text export.
- **Expected behavior:** `allelix stats` recognizes VCF and prints statistics.

### `mhg_grch38_with_grch37_header.txt`
- **Source:** Synthetic MHG (Tempus) fixture. Hand-built from the project's
  `tests/fixtures/mock_myhappygenes_mislabeled.txt` mock-data generator
  output (committed to the repo; expanded here for the library).
- **What it is:** An MHG-format file of about 2,000 variants with positions on GRCh38
  but a `MyHappyGenes [TEMPUS]` header that claims `build 37.1`. Replicates
  the build-mismatch pattern that MHG/Tempus exports have been observed to
  ship with (header lies about build; positions are actually on the newer
  reference).
- **What it tests:** ADR-0021 and ADR-0044 — confident known-SNP positions
  identify GRCh38, the parser reads the header's GRCh37 label, and the
  `Build mismatch:` notice fires. The decided build (GRCh38) is used for
  annotation dispatch; the (wrong) header build is not.
- **Expected behavior:** `allelix analyze` prints:
  - `Build: GRCh38 (from known-SNP positions: 7/7 match GRCh38)`
  - `Build mismatch: the file says GRCh37, but its known-SNP positions say GRCh38 (7/7). Using GRCh38. ...`

### `synthetic_23andme_plain.txt`, `synthetic_23andme_bom.txt`, `synthetic_23andme_blank_first_line.txt`
- **Source:** Synthetic, written by a script for the Allelix tests (the
  header says so). The header's date is a placeholder. The rsIDs are the build-detection known-SNP sites at their
  GRCh37 positions, plus four invented rsIDs (`rs39999901xx`). Every
  genotype is invented.
- **What it is:** One 23andMe-shaped file (banner, column line, 15 rows, one
  `--` no-call, one-letter X and MT calls) in three copies. The copies have
  the same bytes, except that one starts with a UTF-8 byte order mark
  (`EF BB BF`) and one starts with a blank line.
- **What it tests:** A file that starts with a byte order mark or a blank line
  before its vendor banner is read like the plain copy. Checked on test
  files only.
- **Expected behavior:** `allelix stats` reads all three as 23andMe, GRCh37
  (from known-SNP positions), 15 SNPs and 1 no-call. `allelix extract` for
  all 15 rsIDs gives the same table for each copy.

### `synthetic_ancestrydna_lf.txt`, `synthetic_ancestrydna_cr_only.txt`
- **Source:** Synthetic, written by the same script. The same 15 sites and
  invented calls in the AncestryDNA layout (chromosomes 23 and 26 for X and
  MT, `0 0` for the no-call).
- **What it is:** The same file twice: once with Unix (LF) line endings, and
  once with classic Mac OS line endings (CR only, no LF anywhere).
- **What it tests:** CR-only line endings are read like LF. Checked on test
  files only.
- **Expected behavior:** `allelix stats` reads both as AncestryDNA, GRCh37
  (from known-SNP positions), 15 SNPs. `allelix extract` for all 15 rsIDs
  gives the same table for both.

### `synthetic_half_calls.vcf`
- **Source:** Synthetic, written by hand. The header values are
  placeholders. There are four real rsIDs at their GRCh38 positions, with
  invented calls.
- **What it is:** A one-sample GRCh38 VCF (contig lengths only) with one
  ordinary heterozygous call and three half calls, one allele called and the
  other missing: `./1`, `1/.` and `.|1`.
- **What it tests:** Half calls are read and labelled as half calls, not
  dropped and not read as no-calls. Checked on test files only.
- **Expected behavior:** `allelix analyze synthetic_half_calls.vcf
  --min-magnitude 0 --gwas-min-magnitude 0 --snpedia-min-magnitude 0` exits 0
  and prints "Note: 3 half call(s) with one allele not called". The JSON report gives
  `input.vcf_quality.half_calls` = 3. Every row at those three rsIDs has
  zygosity `half_call`, with its genotype shown as the called allele and `.`
  (for example `C/.`); the HTML and terminal show "Half call".

### `synthetic_haploid_calls.vcf`
- **Source:** Synthetic, written by hand. The header values are
  placeholders. The rsIDs are real ClinVar sites on X, Y and MT at their
  GRCh38 positions, with invented calls.
- **What it is:** A one-sample GRCh38 VCF with one diploid autosomal call and
  one one-number (haploid) call (`GT` = `1`) each on chrX, chrY and chrM.
- **What it tests:** A haploid call is shown as Hemizygous with its one
  allele. Checked on test files only.
- **Expected behavior:** `allelix analyze synthetic_haploid_calls.vcf
  --min-magnitude 0 --include-benign` exits 0. The X and Y sites are ClinVar
  Likely benign, so they show only with `--include-benign`; without it only
  the MT site gives rows. In the JSON report, every row on X, Y and MT has
  zygosity `hemizygous` and a one-letter genotype.

## Adding new edge cases

When a parser bug surfaces, add a synthetic file here that reproduces it.
Copy the file's shape: comment block with placeholder values, column line,
delimiter, line endings, no-call and indel codes. Invent every row. Add a
README entry: what shape triggers the quirk, and the expected behaviour
before and after the fix.

Edge case files exist to prevent regressions — they are the test corpus that
catches what fixtures miss.
